# Run Protocol

`judge-run.py start` owns preparation, preflight, admission, and launch for one trial. The committed suite manifest supplies the requested identity. `prepare-run.py` has no selected identity to report yet — nothing has called pi — so it correctly leaves `selected_model: null`. The selected identity is only genuine once `preflight.py`'s admission probe gets a real response back: pi's own assistant message carries `provider`/`model` fields (confirmed against a real captured transcript), and that is the only part of the requested identity pi's event stream independently confirms — there is no analogous server-echoed confirmation for `thinking`, which is a request-time parameter carried through unverified. A provider/model mismatch between requested and served is infrastructure failure: preflight fails outright (never persisting a mismatched identity into `run.json` or `admission.json`), and the harness must be cleaned up and fixed before launching a candidate. The actual candidate session's own transcript is checked again, independently, at collection time (`summarize-run.py`), so a session that never completed a turn, or that shows a different served model than requested, is never scored as identity-verified even if the admission probe minutes earlier was fine.

After launch, the judge follows the timestamped Pi RPC stream and evaluates the actual run. Event reads and runtime, Git, and process inspections are stored with digests and observation IDs. A valid decision must cite event and inspection observations; classification derives a contiguous sequence range from the digest-verified event payloads themselves and requires exact coverage through the terminal lifecycle sequence. Candidate-facing messages are allowed only through `judge-control.py`; pending intent is fsynced before delivery, and both host and candidate journals must agree on delivered interventions. The manifest timeout is passed to the candidate bridge; expiry terminates Pi and writes durable completion evidence.

The user-facing `watch-eval.py` dashboard is a projection of `progress.json`, `campaign.json`, and finalized artifacts, scoped to one campaign at a time — one row per task, grouped by the run IDs `campaign.py add-run` recorded for it. It never controls or judges the candidate. There is no suite- or campaign-wide completion percentage: an active trial reports lifecycle phase and timeout consumption, and a task with no recorded runs reports "not started", never a fabricated percentage.

`collect` owns creation of the final artifact directory and saves canonical Pi RPC JSONL, the timestamped lifecycle and judge-command journal, final dashboard state, session directory, service logs, Git status, diff, health, process snapshot, and selected container metadata. Exact transient provider secrets are redacted from candidate-derived content, structured keys, and filenames in an unpublished staging tree. The complete run tree is scanned before the staged artifacts are atomically published; failed collection removes staging and any empty unpublished final path. It preserves candidate-created regular untracked files under `workspace-untracked/`; traversal paths and symlinks are rejected. Collection is uniformly generic across every task — there is no task-specific oracle branch. Scripts do not copy environment dumps.

`judge-verify.py <run_id> --label <name>` is the judge's on-demand eyes: it drives the candidate container's live `drive.py` to capture a screenshot, runtime state, widget tree, semantics, and settings into `judge-verifications/<observation_id>/`, writes a manifest with a sha256 per artifact, and appends a `kind: "verification"` record to `judge-observations.jsonl` following the same observation-ledger pattern as `judge-inspect.py`.

Run `summarize-run.py <run-id>` after collection and inspect `summary.json` before raw JSONL. It streams the transcript, counts top-level tool execution events rather than repeated updates, and reports bounded final text, completion, usage, Git, and Flutter-evidence fields.

Run IDs are restricted to letters, digits, `_`, and `-`. Each lifecycle command emits one structured JSON object and uses stable exit codes: `2` bad input, `3` missing prerequisite, `4` infrastructure/preflight failure, `5` candidate launch failure, and `6` intervention cap exceeded (`judge-control.py` refuses a 4th delivered intervention; the judge must terminalize the run instead).

`build-image` freezes Pi and its existing managed `npm/` and `git/` package caches into deterministic archives. `prepare-run` freezes the suite identity, the requested model identity (not yet a selected one — see above), exact prompt, limits, platform, task and suite hashes, exact egress hostname, Pi version, config fingerprints, image ID, and trial number. Launch rejects a changed task manifest and uses only the frozen contract. Preflight transfers the same transient configuration over stdin for a real isolated admission request, verifies network and container isolation before any candidate prompt, and persists the genuinely-discovered selected model identity back into `run.json` once the admission probe confirms it — every later stage (launch, `judge-control.py`, `judge-verify.py`, `judge-events.py`, `judge-inspect.py`, `collect.py`) reads it from there.

`interventions.json` starts as `[]`. `steer` and `follow_up` are recorded with one of `clarification`, `recovery`, `verification_request`, `correction`, or `implementation_guidance`. A zero delivered count is `assisted: false`. The cap check and delivery are serialized under an exclusive file lock across the whole read-check-append-write, so `judge-control.py` refuses a 4th delivered intervention (exit `6`) even under concurrent invocations, with no delivery lost from the journal; the judge must terminalize the run instead of continuing to steer. A valid classification must agree with both intervention journals.

Outcome and score are never asserted by the judge directly: `classify-run.py --scorecard <path>` computes `raw`/`penalty`/`adjusted`, the 0-3 score, and the `pass`/`partial`/`fail` outcome from the scorecard against the hashed rubric, with any unmet `required` expectation capping the score at 2. The binding between a scorecard entry and its evidence is per-expectation, not aggregate: every entry's `evidence_ref` must resolve to an observation of the exact `judge-observations.jsonl` kind its own rubric entry declares (`**Evidence:** verification|inspection|events`, defaulting to `verification`) — citing an unrelated `inspection` or `events` observation to settle a `verification`-only expectation is rejected by expectation id, and a cited verification observation with no genuinely successful capture (every drive.py call failed, or every capture hit a content sentinel like `getSemantics`' "semantics not available") does not satisfy "the judge looked." The scorecard file also carries the task id and rubric hash the judge read when writing it; a hash or task mismatch against the run's current state is rejected before scoring, so a rubric edited after the fact, or a scorecard copied from a near-duplicate task, cannot be silently scored. Valid scoring requires model-identity evidence from two independent sources — the admission probe's own served-model report and, separately, the actual candidate transcript's served-model evidence, both compared against the requested identity — plus candidate completion, lifecycle and progress artifacts, a complete cost schema, summary, intervention record, Git evidence, and a scorecard passing all of the above. `model_identity_verified` in `result.json` is a real derived fact, never a hardcoded value: it is `true` only for a `valid` run where both checks passed, and `false` otherwise (including every `invalid_infrastructure`/`unassigned` run, which has no such evidence at all). It covers `provider` and `model` only — `thinking` has no server-side confirmation anywhere in pi's event stream and is not claimed as verified; see references/scoring.md's Known limitations. Provider-unknown cost values remain `null` and render as `unknown`. Cleanup first journals and requests supervisor abort, attempts collection, journals force-removal intent and result, then records a host-side inspection proving the candidate container is absent before infrastructure teardown.
