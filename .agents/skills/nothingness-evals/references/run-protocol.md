# Run Protocol

`judge-run.py start` owns preparation, preflight, admission, and launch for one trial. The committed suite manifest supplies the requested identity; the selected identity is copied separately and must exactly match before preparation, admission, and launch. A failing preflight is infrastructure failure: clean up and fix the harness before launching a candidate.

After launch, the judge follows the timestamped Pi RPC stream and evaluates the actual run. Event reads and runtime, Git, and process inspections are stored with digests and observation IDs. A valid decision must cite event and inspection observations; classification derives a contiguous sequence range from the digest-verified event payloads themselves and requires exact coverage through the terminal lifecycle sequence. Candidate-facing messages are allowed only through `judge-control.py`; pending intent is fsynced before delivery, and both host and candidate journals must agree on delivered interventions. The manifest timeout is passed to the candidate bridge; expiry terminates Pi and writes durable completion evidence.

The user-facing `watch-eval.py` dashboard is a projection of `progress.json` and finalized artifacts. It never controls or judges the candidate. Suite percentage is finalized valid trial slots divided by planned valid slots. An active trial reports lifecycle phase and timeout consumption, not a fabricated candidate-completion percentage.

`collect` owns creation of the final artifact directory and saves canonical Pi RPC JSONL, the timestamped lifecycle and judge-command journal, final dashboard state, session directory, service logs, Git status, diff, health, process snapshot, and selected container metadata. Exact transient provider secrets are redacted from candidate-derived content, structured keys, and filenames in an unpublished staging tree. The complete run tree is scanned before the staged artifacts are atomically published; failed collection removes staging and any empty unpublished final path. It preserves candidate-created regular untracked files under `workspace-untracked/`; traversal paths and symlinks are rejected. For T1 it generates `task-evidence.json` from paired successful Pi tool events and an independent live playback inspection. Scripts do not copy environment dumps.

Run `summarize-run.py <run-id>` after collection and inspect `summary.json` before raw JSONL. It streams the transcript, counts top-level tool execution events rather than repeated updates, and reports bounded final text, completion, usage, Git, and Flutter-evidence fields.

Run IDs are restricted to letters, digits, `_`, and `-`. Each lifecycle command emits one structured JSON object and uses stable exit codes: `2` bad input, `3` missing prerequisite, `4` infrastructure/preflight failure, and `5` candidate launch failure.

`build-image` freezes Pi and its existing managed `npm/` and `git/` package caches into deterministic archives. `prepare-run` freezes the suite identity, requested and selected model identities, exact prompt, limits, platform, task and suite hashes, exact egress hostname, Pi version, config fingerprints, image ID, and trial number. Launch rejects a changed task manifest and uses only the frozen contract. Preflight transfers the same transient configuration over stdin for a real isolated admission request and verifies network and container isolation before any candidate prompt.

`interventions.json` starts as `[]`. `steer` and `follow_up` are recorded with one of `clarification`, `recovery`, `verification_request`, `correction`, or `implementation_guidance`. A zero delivered count is unassisted. A valid pass must agree with both intervention journals; a clean run that fails the oracle may be a valid candidate failure. Valid scoring requires model-identity evidence, candidate completion, lifecycle and progress artifacts, a complete cost schema, summary, intervention record, Git evidence, task evidence, and cited judge observations. Provider-unknown cost values remain `null` and render as `unknown`. Cleanup first journals and requests supervisor abort, attempts collection, journals force-removal intent and result, then records a host-side inspection proving the candidate container is absent before infrastructure teardown.
